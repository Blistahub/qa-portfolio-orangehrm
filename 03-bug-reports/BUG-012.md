# BUG-012 — Los campos del formulario de alta no exponen nombre accesible a un lector de pantalla

| | |
| --- | --- |
| **Severidad** | Media |
| **Prioridad** | Baja |
| **Estado** | Abierto |
| **Módulo** | PIM > Add Employee |
| **Requisito relacionado** | [RNF-03](../00-requisitos.md#6-requisitos-no-funcionales) |
| **Caso de prueba** | [CP-038](../02-casos-de-prueba.md#cp-038) |
| **Entorno** | Chrome (estable) · Windows 11 Pro 24H2 · `opensource-demo.orangehrmlive.com` (OrangeHRM OS 5.x) |
| **Reportado por** | David Coya Moreno |

## Precondiciones

Sesión iniciada con el usuario `Admin`. DevTools abiertas en la pestaña *Elements*.

## Pasos para reproducir

1. Ir a **PIM > Add Employee**.
2. Recorrer el formulario completo usando únicamente la tecla `Tab`.
3. Inspeccionar en las DevTools el marcado del campo *First Name* y de su etiqueta visible.
4. Abrir el panel **Accessibility** de las DevTools y consultar el *nombre accesible* que expone el
   campo con el foco puesto en él.
5. Repetir la comprobación sobre *Middle Name*, *Last Name* y *Employee Id*.

## Resultado esperado

Cada campo del formulario expone un nombre accesible —mediante `<label for="…">`, `aria-label` o
`aria-labelledby`— de modo que un lector de pantalla anuncie qué se está rellenando. Un usuario que
navega sin ver la pantalla debe poder completar el alta.

## Resultado obtenido

- **Navegación por teclado:** correcta. Todos los campos son alcanzables con `Tab` en un orden
  lógico y el foco es visible.
- **Nombre accesible:** las etiquetas visibles están maquetadas como elementos de texto **sin
  asociación** con su campo. El panel *Accessibility* muestra los campos de texto con el nombre
  accesible vacío.

El resultado práctico: un lector de pantalla anuncia *«cuadro de edición»* sin decir cuál. El
formulario es navegable pero no rellenable a ciegas.

## Notas técnicas

El patrón observado en el marcado es que la etiqueta visible y el control son **hermanos dentro de
un contenedor**, sin `for`/`id` que los relacione ni atributo `aria-label` en el control. Visualmente
el usuario ve la etiqueta junto al campo y no percibe ningún problema; el árbol de accesibilidad, en
cambio, recibe un control anónimo.

Corresponde al criterio **WCAG 2.1 · 1.3.1 Información y relaciones (nivel A)** y a
**4.1.2 Nombre, función, valor (nivel A)**. Se citan de forma orientativa: **esto no es una auditoría
de accesibilidad**, que queda fuera del alcance declarado en el
[plan de pruebas](../01-plan-de-pruebas.md). Es una comprobación básica de etiquetado sobre un único
formulario, y así debe leerse el hallazgo.

La corrección es de bajo coste —añadir `for`/`id`, o `aria-label` donde el diseño no permita
etiqueta visible— pero conviene aplicarla al **componente de campo reutilizable**, no formulario a
formulario: el mismo patrón aparece en el resto de pantallas del módulo, por lo que corregir solo
*Add Employee* dejaría el problema abierto en todas las demás.

## Análisis de impacto

Severidad **Media**, prioridad **Baja** en el contexto de este ciclo. La justificación de esa
combinación:

- **Media** y no baja porque no es un problema estético: para un usuario de lector de pantalla el
  formulario de alta de empleados es **inutilizable**, no incómodo. En una aplicación de RRHH
  desplegada en una organización, la accesibilidad puede además ser una exigencia contractual o
  normativa, no una mejora opcional.
- **Baja** en prioridad porque en este ciclo compiten con ella defectos que corrompen el dato maestro
  ([BUG-010](BUG-010.md), [BUG-002](BUG-002.md)), y porque la corrección conviene planificarla sobre
  el componente compartido, dentro de una revisión de accesibilidad más amplia, en lugar de
  parchearla aquí.

## Recomendación

1. Asociar etiqueta y control en el componente de campo reutilizable del sistema de diseño.
2. Verificar el resto de formularios del módulo tras el cambio, que se beneficiarán de la misma
   corrección.
3. Si la accesibilidad es un requisito del cliente, planificar una auditoría específica: este
   hallazgo procede de una comprobación básica y **no debe interpretarse como una medida del estado
   de accesibilidad de la aplicación**.
