# BUG-002 — Un fallo de validación de la contraseña deja el empleado creado sin sus credenciales

## Precondiciones

Sesión iniciada con el usuario `Admin`.

## Pasos para reproducir

1. Ir a **PIM > Add Employee**.
2. Introducir *First Name* `Ana` y *Last Name* `Vidal`.
3. Activar el conmutador **Create Login Details**.
4. Introducir *Username* `avidal.test01` y *Password* `test` (incumple la política: menos de 8
   caracteres y sin dígito).
5. Pulsar **Save**.
6. Ir a **PIM > Employee List** y buscar `Ana Vidal`.
7. Ir a **Admin > User Management** y buscar el usuario `avidal.test01`.

## Resultado esperado

El alta de empleado y la creación de sus credenciales forman **una sola operación**. Si la
contraseña no cumple la política, la operación completa se descarta: se muestra el error de
validación y **no se crea ningún registro**. El usuario corrige la contraseña y vuelve a guardar.

## Resultado obtenido

Se muestra el error de política de contraseña, como corresponde, **pero el empleado `Ana Vidal` ya
figura en Employee List**. En *Admin > User Management* no existe ningún usuario `avidal.test01`.

El resultado es un empleado creado a medias: existe la ficha, no existen las credenciales. Si el
administrador reintenta el alta desde cero corrigiendo la contraseña, obtiene un **segundo registro
duplicado** del mismo empleado.

## Notas técnicas

Este defecto es un problema de **atomicidad**, y las DevTools lo dejan claro. Al pulsar Save se
observan en la pestaña *Network* **dos peticiones consecutivas e independientes**:

1. `POST /web/index.php/api/v2/pim/employees` → **200 OK**, el empleado queda persistido.
2. `POST /web/index.php/api/v2/admin/users` → **422 Unprocessable Entity**, con el detalle del
   incumplimiento de la política de contraseña.

El formulario es una única pantalla para el usuario, pero **dos transacciones separadas** para el
sistema, sin transacción envolvente ni compensación cuando la segunda falla. Por eso el fallo de la
segunda no revierte la primera.

La validación de la contraseña se resuelve además **en el servidor**, no antes de enviar: el cliente
llega a lanzar la primera petición sin haber comprobado que la segunda pueda tener éxito.

## Análisis de impacto

Severidad **Alta** por tres motivos concretos:

- **Corrupción del dato maestro.** Genera empleados duplicados en el sistema de RRHH, con la
  consiguiente ambigüedad en nóminas, permisos y jerarquías.
- **Frecuencia alta.** Fallar la política de contraseña al primer intento es un error de usuario
  cotidiano, no un caso extremo. El camino de error es el habitual.
- **Reparación manual.** El administrador debe localizar y borrar el registro huérfano; si no
  advierte que se creó, el duplicado permanece.

## Recomendación

Dos correcciones complementarias:

1. **Servidor:** envolver ambas operaciones en una única transacción, o exponer un endpoint de alta
   que reciba empleado y credenciales juntos y valide todo antes de persistir nada.
2. **Cliente:** validar la política de contraseña antes de lanzar la primera petición, para que el
   camino de error habitual no llegue siquiera a tocar el servidor.

La corrección (2) por sí sola reduce la frecuencia, pero deja el defecto abierto para cualquier
consumidor directo de la API. La (1) es la que cierra el problema.
