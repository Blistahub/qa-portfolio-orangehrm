# BUG-001 — Los campos de nombre aceptan cadenas numéricas y símbolos sin validación de formato

## Precondiciones

Sesión iniciada con el usuario `Admin`.

## Pasos para reproducir

1. Ir a **PIM > Add Employee**.
2. Introducir en *First Name* el valor `12345`.
3. Introducir en *Last Name* el valor `!@#$%^&*()`.
4. Pulsar **Save**.
5. Volver a **PIM > Employee List** y buscar el registro recién creado.

## Resultado esperado

El formulario rechaza la entrada y muestra un mensaje de validación de formato bajo los campos
afectados. Un nombre de persona no admite dígitos ni símbolos de puntuación.

## Resultado obtenido

El formulario acepta ambos valores, muestra el aviso *«Successfully Saved»* y crea el empleado. El
registro aparece en el listado con `12345 !@#$%^&*()` como nombre completo. La única restricción
aplicada es la de longitud (30 caracteres); no existe ninguna sobre el conjunto de caracteres
admitidos.

## Notas técnicas

Inspeccionando la petición en la pestaña *Network* de las DevTools, el alta se envía como
`POST /web/index.php/api/v2/pim/employees` con un cuerpo JSON del tipo:

```json
{ "firstName": "12345", "middleName": "", "lastName": "!@#$%^&*()", "empPicture": null }
```

La respuesta es **200** y devuelve el recurso creado con `empNumber` asignado. Es decir, **la
validación de formato no falta solo en el cliente: tampoco existe en el servidor**. Cualquier
integración que consuma este endpoint (importación masiva de empleados, sincronización con una
nómina externa) podrá introducir nombres inválidos sin obstáculo alguno.

Reproducido igualmente en Firefox y Edge, lo que confirma que no depende del navegador.

## Análisis de impacto

No provoca pérdida de datos ni bloquea ningún flujo, de ahí la severidad Media. El impacto real es
de **calidad del dato maestro**: el nombre del empleado alimenta listados, informes, nóminas y
comunicaciones. Un registro con símbolos se propaga a todos ellos y su corrección posterior es
manual.

## Recomendación

Aplicar una validación de conjunto de caracteres en el **servidor** —letras Unicode, espacios,
apóstrofo y guion, para no excluir apellidos como *O'Brien* o *García-López*— y replicarla en el
cliente para dar realimentación inmediata. Corregir solo el cliente dejaría el endpoint expuesto.

## Verificación

Reproducido. La petición de alta se envía como
`POST /web/index.php/api/v2/pim/employees` y responde **200** con el recurso creado:

```jsonc
// petición
{ "firstName": "12345", "middleName": "", "lastName": "QaTest001", "empPicture": null }
// respuesta 200 → data.empNumber asignado
```

Segunda comprobación con símbolos en el apellido —`"lastName": "!@#$%^&*()"`— igualmente **200**.
Ninguna de las dos entradas produce mensaje de validación en el cliente ni en el servidor.
